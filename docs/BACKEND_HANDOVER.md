# تسليم الباك إند — سفير

هذه الوثيقة للمبرمج الذي سيستلم الباك إند. اقرأها قبل كتابة أي سطر.

## 0. الخلاصة أولًا
- **الباك إند ليس صفحة بيضاء.** هو مبني على Supabase:
  - PostgreSQL مع RLS: 13 ترحيلًا، و51 جدولًا، و81 دالة، و12 عرضًا.
  - 9 دوال Edge بلغة Deno.
  - 12 حزمة اختبارات سلوك على قاعدة حقيقية.
  - 61 اختبار وحدة، و4 اختبارات لوصلة الشحن.
- قواعد المال (التسعير، والعمولات، والحجز، والتسوية، والدفتر المزدوج، والفواتير المتسلسلة) **مكتوبة ومختبرة في SQL**.
- **التوصية:** أكمل على Supabase ولا تُعِد البناء بإطار آخر. إعادة البناء تعني إعادة كتابة منطق مالي مختبر واختباراته، بلا مكسب للمنتج. إن كان لا بد من خادم إضافي (Node أو Laravel مثلًا)، فليكن **لتكاملات خارجية فقط** يستدعي دوال قاعدة البيانات نفسها، لا ليحل محلها.
- ما المطلوب منك فعلًا؟ القسم 8.

## 1. المعمار
```
المتصفح (React + Vite)
  │  قراءة مباشرة بمفتاح anon ← RLS تقرر ماذا يرى كل دور
  │  كل كتابة حساسة ← supabase.rpc('…')  (دوال SECURITY DEFINER تتحقق من الصلاحية بنفسها)
  ▼
PostgreSQL (Supabase)
  ├─ الدفتر المزدوج: post_txn() فقط، الجدول append-only، وتوازن كل قيد
  ├─ الإعدادات التجارية بنسخ وتواريخ سريان: platform_settings ← active_settings()
  ├─ الفواتير: ترقيم سنوي وسلسلة بصمات SHA-256
  └─ محفزات: التوجيه للمستودع، الإشعارات، توثيق المصانع، الأوزان، القبول القانوني
Edge Functions (Deno)
  create-order        تسعير الخادم + فتح الدفع (لا يُقبل سعر من المتصفح)
  payment-webhook     Moyasar → confirm_payment() + منع التكرار
  shipping            المجمّع: الأسعار، البوليصة، التتبع (manual | http)
  shipment-update     Webhook التتبع (HMAC أو سر مشترك) + منع التكرار
  commission-engine   cron يومي → run_nightly()
  notify-dispatch     cron 10 دقائق → البريد + واتساب
  health              cron 15 دقيقة (POST) + مراقبة خارجية (GET)
  track-click         نقرات روابط السفراء (حد لكل IP)
  cms-upload          رفع وسائط المحتوى (المدراء فقط)
```
الشرح الكامل لكل دالة ومن يحق له استدعاؤها، في [`API_CATALOG.md`](API_CATALOG.md). يُولَّد آليًا بالأمر `python3 scripts/gen-api-catalog.py > docs/API_CATALOG.md`.

## 2. قواعد لا تُكسر
1. **السعر يُحسب في الخادم فقط** (`_shared/pricing.ts` و`priceOrder`). أي مبلغ يأتي من المتصفح يُتجاهل.
2. **المال لا يتحرك إلا عبر `post_txn()`.** القيود لا تُعدَّل ولا تُحذف، والتصحيح يكون بقيد عكسي.
3. **حالات العمولة:** `pending ← eligible ← paid`، أو `void`. لا تُصرف قبل التسليم وانقضاء مدة الإرجاع في بلد الوصول.
4. **الأدوار من `user_roles` فقط.** لا تُقرأ الصلاحيات من `user_metadata` أبدًا، فالمستخدم يعدّلها بنفسه.
5. **كل جدول عليه RLS.** الدالة الجديدة التي تكتب تكون `security definer` وتتحقق من المستدعي، ثم: `revoke … from public, anon` ثم `grant` للدور المقصود. PostgreSQL يمنح PUBLIC صلاحية التنفيذ افتراضيًا، والكتالوج كشف ثلاث دوال مكشوفة بهذا السبب وأُغلقت في الترحيل 012.
6. **المدير يحتاج تحققًا ثنائيًا** (`aal2`) ما دام `requireMfaForAdmin` مفعّلًا.
7. **كل Webhook:** يُوثَّق (توقيع أو سر)، ويُسجَّل في `webhook_events`، ولا يُعالج مرتين.
8. **الإعدادات التجارية لها نسخة في الخادم:** بعد أي تعديل على `src/config/platform.ts` نفّذ `npm run sync:shared`، واختبار التطابق يفشل إن نُسي.
9. **الوثائق القانونية لها إصدارات:** انظر `LEGAL.md`. لا تغيّر نصًا ساريًا دون إصدار جديد.

## 6. الاختبارات (كلها في CI)
```bash
npm run type-check && npx eslint src && npm test          # 61 اختبار وحدة
npm run test:functions                                     # وصلة المجمّع مقابل مجمّع وهمي
PGHOST=… PGPORT=… PGUSER=… npm run test:db                # 12 حزمة سلوك على PostgreSQL
python3 scripts/gen-client-queries.py > supabase/tests/07_client_queries.sql   # بعد تعديل استعلامات الواجهة
```
**القاعدة:** كل دالة جديدة تأتي مع اختبار في `supabase/tests/` يغطي المسار الصحيح، ورفض غير المصرَّح له، وتوازن الدفتر إن مسّت المال.

## 9. حدود يجب أن تعرفها
- الشاشات الحية اختُبرت مقابل خادم وهمي يحاكي Supabase، وقاعدة البيانات اختُبرت على PostgreSQL 16 محلي. **لم يُختبر شيء على مشروع Supabase حي بعد**، وهذا البند 1.
- 27 شاشة ما زالت توضيحية، وتظهر للحساب الحقيقي مع تنبيه صريح (`AUDIT_REPORT.md` القسم 3).
- ترجمة الأردية والإندونيسية لا تغطي شاشات الإصدارات 7.3–7.5، فتظهر بالإنجليزية.
- الشحن يعمل يدويًا حتى ربط المجمّع.
