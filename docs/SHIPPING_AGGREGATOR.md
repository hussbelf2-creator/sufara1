# ربط منصة تجميع الشحن — دليل الاختيار والتنفيذ

المنصة جاهزة للربط: الشاشات والجداول وسير العمل لا تتغير. يتغير **ملف واحد** فقط: `supabase/functions/_shared/shipping-provider.ts`.

## 1. ما يجب أن توفّره المنصة قبل التوقيع
اطلب من المزوّد إثباتًا عمليًا (بيئة Sandbox) لكل بند:

| # | المتطلب | لماذا |
|---|---|---|
| 1 | **واجهة أسعار** لكل ناقل وخدمة، بالوزن والدولة | شاشة التجميع تعرض العروض وتختار |
| 2 | **إصدار بوليصة** يعيد رقم التتبع ورابط الملصق | يُطبع الملصق من المستودع |
| 3 | **منع التكرار** (Idempotency-Key أو مرجع فريد) | ضغطة مكررة يجب ألا تحجز بوليصتين |
| 4 | **Webhook للتتبع** مع توقيع HMAC أو سر مشترك | «تم التسليم» يبدأ نافذة الإرجاع ثم صرف العمولات، فلا يُقبل من مصدر غير موثّق |
| 5 | **تغطية الدول**: إندونيسيا، باكستان، مصر، الخليج، ماليزيا، تركيا | قنوات الحجاج والمعتمرين الأولى |
| 6 | **شحن DDP** (الرسوم الجمركية على المرسل) | الأسعار في المتجر شاملة للجمارك |
| 7 | **ناقلون محليون** في الوجهات (J&T وJNE وTCS وLeopards) | آخر ميل أرخص من الناقل الدولي |
| 8 | **الإرجاع** (Return label) | سياسة الإرجاع حسب بلد الوصول |
| 9 | **فوترة شهرية بالريال** وتقرير لكل بوليصة | للمطابقة مع `shipments.cost` |

## 2. ما يتوقعه المشغّل الحالي (`httpDriver`)
إن طابقت واجهة المزوّد هذه الأشكال فالربط **إعدادات فقط**. وإلا تُعدَّل أسماء المسارات والحقول داخل الدالة نفسها.

| العملية | الطلب | الرد المتوقع |
|---|---|---|
| الأسعار | `POST /rates` ← `{ originCountry, originCity, destinationCountry, weightKg, parcels }` | `{ rates: [{ carrier, service, amount, min_days, max_days }] }` |
| البوليصة | `POST /shipments` + `Idempotency-Key: <shipment id>` ← المرسل والمستلم والطرود (الوزن، الوصف، القيمة، رمز HS) والـ Incoterm | `{ id, tracking_number, label_url, cost }` |
| التتبع | `GET /shipments/{id}/events` | `{ events: [{ status, timestamp, description, location }] }` |

يتولّى المشغّل حاليًا: مهلة 15 ثانية، وإعادة المحاولة مرتين للقراءات عند أخطاء الشبكة أو 5xx، وعدم الإعادة عند 4xx مع إظهار رسالة المزوّد، وتحويل حالات الناقل إلى حالات المنصة الخمس (`mapCarrierStatus`). الحالات غير المعروفة تُتجاهل ولا تُخمَّن.

## 3. Webhook التتبع
- العنوان: `https://<project>.supabase.co/functions/v1/shipment-update`
- التوثيق: إن دعم المزوّد التوقيع فاضبط `SHIPPING_WEBHOOK_HMAC_SECRET`، والترويسة `x-signature` = HMAC-SHA256 للنص الخام (تُقبل بادئة `sha256=`). وإلا فاضبط `SHIPPING_WEBHOOK_SECRET`، والترويسة `x-carrier-secret`.
- الجسم: `{ "tracking_no": "…", "status": "Delivered", "at": "…", "description": "…", "location": "…" }`. الحالة تُحوَّل تلقائيًا، والأحداث المعادة (نفس الشحنة والحالة والوقت) تُتجاهل.

## 4. خطوات التشغيل
1. `supabase secrets set SHIPPING_PROVIDER=http SHIPPING_API_URL=… SHIPPING_API_KEY=… SHIPPING_WEBHOOK_HMAC_SECRET=…`
2. `supabase functions deploy shipping shipment-update`
3. من «الشحن واللوجستيات» حوّل نمط الناقلين المتعاقد عليهم إلى «عبر المجمّع».
4. جرّب شحنة واحدة في Sandbox: تجميع ← بوليصة ← أحداث ← «تم التسليم» ← تظهر في «طلباتي» لدى المشتري ويصله إشعار.

## 5. الاختبار
`npm run test:functions` يشغّل المشغّل مقابل مجمّع وهمي محلي، ويتحقق من: الأسعار مع إعادة المحاولة، البوليصة مع منع التكرار، تحويل الحالات، رفض 4xx دون إعادة، المهلة، واختيار المشغّل من الإعدادات. بعد كتابة مشغّل المزوّد الفعلي يُضاف له اختبار بنفس النمط.
