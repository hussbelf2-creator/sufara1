## Edge Functions

### `cms-upload`

Uploads a CMS media file (video or image) for the admin content panel. Hardening (audit §4): - Caller must present their own session token and hold the admin role (user_roles) — the anon key alone is refused. - CORS is limited to ALLOWED_ORIGINS. - Size limits come from env (defaults 8 MB image / 60 MB video), the MIME type is checked against the file's magic bytes, not only the header. - Each admin is rate-limited (UPLOADS_PER_HOUR, default 30). - The file lands in the public `media` bucket under cms/ and is returned as its public URL — no year-long signed links. Every upload is written to the audit log.

### `commission-engine`

Nightly job (Supabase cron → POST with header x-cron-secret). run_nightly(): settles sub-orders whose destination return window closed, unlocks commissions, re-tiers ambassadors, and closes group orders past their deadline (short groups go to the admins for a decision).

### `create-order`

Creates an order from ids and quantities only and opens the payment. Nothing the browser computed is trusted: prices, tiers, the discount cap, shipping, customs, VAT, the channel and the ambassador attribution are all recomputed here from the database and the active PlatformConfig version, whose number is stamped on the order.

### `health`

Health endpoint. GET (public, for an external uptime monitor — UptimeRobot, Better Stack…) → 200 { status: "ok" | "warn" } or 503 { status: "fail" | "down" }. No details are exposed; the database being unreachable reads "down". POST (cron every 15 minutes, header x-cron-secret) → health_sweep(): compares every check with its last state and, on a change only, alerts the admins in the dashboard AND by e-mail right away (not through notify-dispatch, which may be the broken part).

### `notify-dispatch`

Every few minutes (cron, x-cron-secret): • e-mails the notifications not e-mailed yet — account holders at their auth e-mail, guests at the e-mail on their order, admin notifications to ADMIN_EMAILS; • sends WhatsApp for kinds that have an active (Meta-approved) template in whatsapp_templates, only to numbers that opted in (profile or checkout).

### `payment-webhook`

Moyasar webhook (payment_paid / payment_refunded / payment_failed). - Authenticity: the shared secret configured in the Moyasar dashboard is compared in constant time, then the payment is re-fetched from the Moyasar API so the amount and status come from the provider, not from the request body. - Idempotent: confirm_payment() ignores an order that is already paid. - Money: capture, escrow, reserve and commission rows are written in one database transaction by confirm_payment(); the tax invoice number is issued by issue_invoice() right after. Note on "holding" funds: card authorisations expire within days, so the 30–60 day export return window cannot be held on the card. The money is captured and held in the customer-escrow ledger account; the factory and the ambassador are paid only after run_commission_engine() releases it.

### `shipment-update`

Tracking webhook from the shipping aggregator. Authentication — whichever the aggregator supports: • SHIPPING_WEBHOOK_HMAC_SECRET set → header x-signature must be the hex HMAC-SHA256 of the raw body (an optional "sha256=" prefix is accepted); • otherwise header x-carrier-secret must equal SHIPPING_WEBHOOK_SECRET. Re-sent events (same shipment, status and time) are acknowledged and ignored. Body (shipment level — the normal case after integration): { tracking_no, status: in_transit|out_for_delivery|delivered|exception|returned, at?, description?, location? } Body (sub-order level — kept for manual tools): { sub_order_id, status: dispatched|delivered|returned, at?, tracking_no? } A carrier-confirmed "delivered" starts the destination return window, the clock that unlocks commissions and the factory settlement.

### `shipping`

Warehouse ↔ shipping aggregator (admin only). POST { action: 'status' } → which driver is active POST { action: 'rates', warehouse, country, weightKg } → carrier quotes POST { action: 'label', shipment } → book + label + tracking no. POST { action: 'track', shipment } → pull events now

### `track-click`

Records a visit to an ambassador page and returns an opaque click id. The click id — not a typed code — is what proves the visit when the order is created. Abuse controls: IP and user agent are stored only as salted hashes, and one IP may record at most CLICKS_PER_IP_HOUR clicks an hour.
